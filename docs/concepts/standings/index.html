Standings

Overview​

Every table the factory orders is ordered by one standings engine:

TableWherePolicy
A round-robin grouptallyParticipantResults, written to each position assignment's tally on every resultthe round-robin tally policy
A season table (per tier)seasonGovernor.getSeasonStandingsa season's or tier's tallyPolicy (the same policy)
A competition leaderboard (Swiss, DrawMatic)getCompetitionLeaderboardthe competition policy's victoryPolicy
The best finishers of a position across groupsplayoff entry selection (best-of playoffs)the tally policy's crossGroup

A standing is a pure function of the results: nothing is folded into stored state as results arrive, so a corrected result counts once, as corrected, and a removed result does not count. What is stored on a record (a tally, a competition state) is a cache of that function.

The engine is sport-agnostic. It reads results, not a sport: wins, draws, sets, games or points, and the statuses a result ended with. The sports section below sets out which competitions' rules it can express today, and which it cannot yet.

How an order is decided​

  1. The ledger. Each participant's results are counted: matchUps won, lost and drawn; sets, games and points; lines of a TEAM matchUp; walkovers, defaults and retirements; the opponents beaten, lost to and drawn with. A policy can add classification points per result (resultPoints).
  2. The primary measure (groupOrderKey) partitions everyone, higher first.
  3. Disqualification. With disqualifyWalkovers / disqualifyDefaults, a participant who conceded one is ordered below everyone who did not.
  4. Directives refine each tied set, in order. The first directive that separates a set decides it. A directive can read the whole table or only the meetings among the tied participants (idsFilter: a mini-league).
  5. Splits. When a directive separates some of a tied set, onSplit decides what happens to each smaller set:
    • RESTART (default): it goes back to the first directive.
    • CONTINUE: it resumes with the next directive.
    • EXTRACT_ONE: one participant is placed at a time.
  6. The final step (terminal) settles a set no directive separates:
    • an organiser's sub-order (ADJUDICATE, the default);
    • a shared place (SHARE);
    • a draw seeded so it is reproducible (LOT).
  7. Positions are competition ranks: participants level on everything share a place (1, 2, 2, 4).

While results are outstanding the order is provisional (provisionalOrder), and directives marked when: { phase: 'FINAL' } wait for the end. A group is complete when every meeting has a result, so a double round robin completes like a single one.

A season table adds valueWon and valueLost: the TEAM tie score summed (lines, points or games won).

Precision is a rule, not a display setting: percentages and ratios equal to precision decimal places (default 3) tie, and precision: 'EXACT' compares them unrounded. A percentage with nothing played is 0; a ratio with nothing lost ranks first, unless a directive's zeroDivision says otherwise.

The full policy reference, with every field, is Round Robin Tally Policy.

A policy at a glance​

{
  roundRobinTally: {
    groupOrderKey: 'classificationPoints',
    resultPoints: { rules: [{ id: 'win', winner: 3, loser: 0 }, { id: 'draw', isDrawn: true, points: 1 }] },
    tallyDirectives: [
      { attribute: 'classificationPoints', idsFilter: true }, // the mini-league among the tied
      { attribute: 'pointsDiff', idsFilter: true },
      { attribute: 'pointsDiff' },
      { attribute: 'pointsWon' },
    ],
    onSplit: 'RESTART',
    terminal: 'LOT',
    crossGroup: [{ attribute: 'classificationPoints' }, { attribute: 'pointsDiff' }],
  },
}

A policy is checked where it is saved (attachPolicies, validateSeason, or validateTallyPolicy on its own): an unknown measure, a malformed directive or invalid result rules are refused before anything is written.

Sports and competitions​

The engine was designed against the published standings rules of competitions across sports, not only tennis. For each one below, the table gives what its rules need, how a policy expresses that, and whether the engine supports it today.

  • Supported: the whole procedure can be written as a policy.
  • Partial: the main procedure can, but a named step needs data or a feature the engine does not have yet.
  • Not yet: the deciding criterion depends on data the factory does not record.

Rulebooks are named by document and edition. Where the rule set was read only in secondary sources, it is marked so; presets are written only from rulebooks read at source.

Not yet supported, and why​

Each of these needs an input the factory does not have yet, not a change to how the engine orders:

  • Withdrawn and expunged participants (USTA's conditional expunge): needs who withdrew.
  • Division or conference pre-reduction (NFL wild card, NBA division winners): needs a grouping of participants.
  • Common opponents and record against a tier (NFL, NBA, IIHF): needs the tier or opponent set.
  • Draws in timed aggregate formats (football, handball, hockey regulation): a level result is not yet recorded as a drawn result, so a draw cannot earn its points.
  • Result categories beyond win, draw and loss (hockey regulation versus overtime, rugby bonus points): needs the result to record them.
  • Rates from match statistics (cricket's net run rate): needs the statistics.
  • Unplayed-round handling in chess (FIDE's virtual opponent): not built.
