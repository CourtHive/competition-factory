Hosting factory on a server

A server handles many requests at once. Engine state lives in the installed state provider, and the default provider holds one state for the whole process, so on a server every request would read and write the same records. Install an async state provider, give each request its own state, run its mutations with tournamentEngineAsync as one executionQueue, and save the record only when the queue succeeds.

This page covers that pattern, the methods each exported engine carries, and the bundling hazard that can leave a shared engine without a method TypeScript says it has.

Choose the engine​

EngineWhat it isOn a server
tournamentEngineAsync, competitionEngineAsyncOne async engine instance, exported under two names, with every governor imported by its own moduleUse this for mutations
asyncEngineA factory function. Each call returns an async engine with core methods onlyUse it to assemble your own method set
tournamentEngine, syncEngine, scaleEngineOne sync singleton under several namesNever under the default, process-wide provider
askEngineA sync singleton that dispatches without notificationsThe reference server uses it for queries

Every engine reads and writes through the installed provider. Under the default provider that is one process-wide state, which is why a sync engine is unsafe for concurrent requests. An async provider binds a state to the current async execution context, so two concurrent requests never touch each other's records, whichever engine they call. The async engine also awaits each method and each subscription handler, which the sync engines do not. See Engine Lifetimes and Shared State for how the sync engines share state.

Install an async state provider​

The provider is not exported from the package. Copy the reference implementation, src/examples/asyncEngine/asyncGlobalState.ts, into your server. It is built on AsyncLocalStorage, and it keeps records, subscriptions, notices and the method registry per context. The reference server, competition-factory-server, runs a copy of it; this page cites that server's patterns.

Wrap every entry point in asyncGlobalState.runWithInstanceState(fn). The state is scoped to the callback and every async step it spawns, so it cannot outlive the request or reach a sibling. State touched outside a wrapped entry point gets an implicit per-context state and a console warning. That is a safety net, not isolation: asyncGlobalState.implicitContextCreations() counts those creations, and a non-zero count in production is an unwrapped entry point to find. The provider contract and the rejected alternatives are in Asynchronous State Provider.

Register methods globally for executionQueue​

tournamentEngineAsync attaches every governor method to itself when its module is evaluated. That happens before your startup code installs the async provider, so the method registry those imports also write to belongs to the default provider. Under the async provider, each fresh request state starts with an empty registry.

Direct calls (tournamentEngineAsync.addEvent(...)) and execute({ method }) find the method on the engine. executionQueue resolves each directive only from the registry: the global methods plus the current state's methods. Without a global registration it refuses the queue with METHOD_NOT_FOUND. Register the governors globally once, at startup, as the reference server does:

import { globalState, governors } from 'tods-competition-factory';

globalState.setStateMethods(governors, true, 1, true); // traverse, depth 1, global

From the release that includes #6564, a queue also resolves the methods the engine itself imported, so tournamentEngineAsync needs no global registration. Registering globally stays correct. An engine assembled with asyncEngine() inside the request already finds the methods it imports there.

For a server-defined method, register its private implementation on the engine used by the request. Preview checks every directive before dispatch and returns ERR_UNREGISTERED_PREVIEW_METHOD for a custom method without a registration. Previewing custom methods

Handle a request​

Each mutation request follows the same steps, all inside one runWithInstanceState scope:

  1. Serialize writes per tournament. The factory does not do this. The reference server takes a per-tournament lock inside the request's state scope, then fetches the record.
  2. Load the record with setState. It makes a deep copy by default, so the engine works on its own copy.
  3. Run the mutation as executionQueue(methods). Every directive's method is resolved before any runs. A queue that completes returns { success, results }. A refused queue stops at the refusal and keeps the directives before it in the request's records.
  4. Save only on success. Read the mutated record back from the engine and persist it only when the queue returned success, and discard the request's records otherwise. The reference server saves only then.

A server that saves only whole successes and discards a refused request's records needs no in-memory rollback: the stored record already is the rollback, and executionQueue(methods, true) would only add a deep copy of every loaded record to each request. The reference server runs its engine with rollback off whatever the caller sends, and reports a refused queue to the caller as rolled back (rolledBack: true, no committed), because nothing of it was stored.

With rollback off, a refused queue delivers the notices of the directives it kept before the refusal (see Transaction Pattern). A server that acts on notices, by broadcasting them or writing audit rows for example, must do so only after the save succeeds.

error and success live on the shared instance

setState returns the engine itself, with error and success set on it. tournamentEngineAsync is one object for every request, so read them from the return value at once. Do not read tournamentEngineAsync.error later.

Minimal example​

Framework-neutral. storage and withTournamentLock stand for your record store and your per-tournament mutex.

import { globalState, governors, topicConstants, tournamentEngineAsync } from 'tods-competition-factory';
import asyncGlobalState from './asyncGlobalState'; // your copy of the reference provider

// Once, at startup
globalState.setStateMethods(governors, true, 1, true); // executionQueue resolves methods by name from here
globalState.setStateProvider(asyncGlobalState);

export function runMutation({ tournamentId, methods }) {
  return asyncGlobalState.runWithInstanceState(() =>
    withTournamentLock(tournamentId, async () => {
      // subscriptions belong to this request's state
      const addedEvents = [];
      globalState.setSubscriptions({
        subscriptions: { [topicConstants.ADD_EVENT]: (payloads) => addedEvents.push(...payloads) },
      });

      const tournamentRecord = await storage.load(tournamentId);
      const { error } = tournamentEngineAsync.setState(tournamentRecord);
      if (error) return { error };

      // rollback off: a refused queue is never saved, so the stored record is the rollback
      const result = await tournamentEngineAsync.executionQueue(methods);
      if (result.success) {
        await storage.save(tournamentEngineAsync.getTournament().tournamentRecord);
        // fan out addedEvents here, only after the save
        return result;
      }
      // nothing was stored: drop what a refused queue delivered, and say that nothing was kept
      addedEvents.length = 0;
      const { committed, results, ...refusal } = result;
      return { ...refusal, rolledBack: true };
    }),
  );
}

With Express or Nest, call runMutation from the route handler. The reference server instead wraps every request in runWithInstanceState with a middleware, and opens a scope again for each mutation.

Notices and fan-out​

Subscriptions are delivered after a queue completes. A refused queue with rollback delivers nothing; without rollback it delivers the notices of the directives it kept, which a server that does not save the refused queue must drop, as the example does. Under the async provider subscriptions are part of the request's state, so set them in one of two ways:

  • Per request, with globalState.setSubscriptions({ subscriptions }) inside the scope, as in the example.
  • Once, for every context, with globalState.setGlobalSubscriptions({ subscriptions }) at startup.

If you build engines with asyncEngine() instead, construct the engine first and set subscriptions after: constructing an async engine binds a fresh state to the context, which drops subscriptions set before it. The reference server registers its handlers right after construction for this reason. Topics and payloads are in Subscriptions.

Mutation locks​

Mutation locks control who may mutate a scope. They are stored in the record and checked by a lockToken match, and a call without the right token is refused with MUTATION_LOCKED. They do not serialize concurrent requests. That remains your server's per-tournament lock.

Draw-level stamps​

After a mutation the engine stamps the factory { version, timeStamp } on the tournament record. stampScope('modified') opts in to stamping what changed instead: each modified drawDefinition, and the tournament only when something outside its draws changed. A storage layer that keeps a tournament in parts can then write one draw for a score entry.

The setting is process-wide, not per request. It needs the provider's optional cycleModifiedTopics hook to identify draw-only changes; the reference provider implements it. The default is 'tournament'. Making 'modified' the default in 8.0.0 is proposed, not decided. See stampScope.

Which governors each engine carries​

The package is built one module per file and declares "sideEffects": false. A bundler keeps only the modules your code reaches, so a shared engine carries only the methods attached by modules that made it into that bundle.

The sync names are one instance. scaleEngine is syncEngine with the ranking and ratings methods attached. In a bundle that also imports tournamentEngine, it carries every governor. In a bundle that imports only scaleEngine, it carries core methods plus ranking and ratings, so scaleEngine.getMutationLocks (a tournamentGovernor method) is missing. TypeScript cannot tell the two bundles apart. In Node without a bundler, loading the package evaluates every module, so every sync name carries every governor.

How to read it:

  • Generated, by node scripts/generateEngineGovernors.mjs (--check fails on drift). Each engine is bundled alone with esbuild and its function keys are matched by name against each governor's functions.
  • Methods counts every function on the engine. Not from those governors counts the rest: core methods such as setState and executionQueue, and methods attached individually, such as the ratings methods on scaleEngine.
  • Same instance as comes from a second bundle that loads every engine module together. The sync names share one object; the async instance shares nothing with them.
  • sanctioningEngine and officiatingEngine are built from their own method lists, not by importing a governor, so most of their governor's methods appear under the same names and a few do not.

What a missing method looks like​

How you call a missing method decides how it fails:

import { scaleEngine } from 'tods-competition-factory';

// a direct property call throws: TypeError: scaleEngine.getMutationLocks is not a function
scaleEngine.getMutationLocks();

// by name, the engine returns an error instead of throwing
scaleEngine.execute({ method: 'getMutationLocks', params: {} });
// { error: METHOD_NOT_FOUND, methodName: 'getMutationLocks' }

scaleEngine.executionQueue([{ method: 'getMutationLocks', params: {} }]);
// { error: METHOD_NOT_FOUND, methodName: 'getMutationLocks' }, and no directive has run

METHOD_NOT_FOUND is errorConditionConstants.METHOD_NOT_FOUND (code ERR_NOT_FOUND_METHOD).

Avoiding it​

  • On a server, use tournamentEngineAsync. Its own module imports every governor, so it carries the full surface in any bundle. Register the governors globally for executionQueue, as above.

  • If you use a shared sync engine, import what you call, once, at startup. Importing by name keeps the bundle small:

    import { scaleEngine, tournamentGovernor } from 'tods-competition-factory';

    scaleEngine.importMethods({ getMutationLocks: tournamentGovernor.getMutationLocks });

    Imported methods accumulate for the life of the process, and on the sync names they reach every alias. Configure them in one module, not from each route.

  • Prefer execute or executionQueue by name where a missing method should come back as an error result rather than a throw.

Not available​

  • A keep-warm engine. Each request loads its record. Nothing in the engine keeps a record in memory between requests.
  • An exported state provider. You copy the reference provider. setStateProvider checks for the required method names at run time and throws Global state provider is missing required methods when one is absent. From the release that includes #6561, the exported StateProvider type describes the required and optional members, so a missing one also fails at compile time.
