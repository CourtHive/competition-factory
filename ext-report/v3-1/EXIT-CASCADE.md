# Planning an exit and its downstream placements

**VERIFIED.** In the post-schedule-pilot suite census, 3,972 successful whole-call recordings first abstained for exit and 2,314 for cascade. Together they account for 6,286 of 9,395 recordings (66.9%). The largest two groups are both winner routes. A route identifies dispatch, and the reason identifies the first uncovered planner obligation. Neither tells us how many seats a particular call touched. A draw-type restriction alone cannot certify a move. [Full reason × draw type × route table](cells.md)

## One projected draw for both families

**BELIEVED design.** Resolve the call against its input under §3. Snapshot both feeders, current assignments, prior double exits and the decider before planning. The key for a landing includes structure, matchUp, side, draw position and the source that earned it. For each withdrawal, find where the participant or claim actually stands. A converted record can put it somewhere other than the link's nominal target. Fold a complete candidate into a private working view. Recompute later landings from that view after each release or advance. If ownership is ambiguous or a settle predicate still reports work, hand the whole call to the recorder before applying anything.

1. **Before direction.** Use the existing ordered refusals. Resolve progression and scoring policy at the call, including explicit false values. Row 12 tests first-match loser eligibility using the player's actual prior match history. Preserve row 22 correction-kind and row 14 activity checks in their existing order. Row 31 checks a held winner seat and a held loser seat before the first write, including the first award of an undecided dual after #6487. The §2 table's blanket dual exclusion predates that fix. A replaced winner's own seat and a yielding propagated BYE can become free. An unrelated participant's seat cannot.
2. **Placing an exit.** Use the existing result and provenance ops for the origin (`setMatchUpResult`, `setSideExitProvenance`). Represent a reservation with the existing assignment/BYE ops on the actual structure and matchUp. With carry switched off, direct the eligible loser ordinarily. With carry on, resolve retirement policy before choosing the delivered status. Preserve the source origin through a BYE relay (`mergeSideExitProvenance`); it can outlive the current result. With a missing second feeder keep the landing pending. With both feeders present, derive the convergence from their two origins and apply the resulting advance exactly once.
3. **Withdrawing and re-entering.** Reverse a dependency only when the prior source earned it. Clear its position and reservation, preserve the opposite side's independent origin and walk the displaced award onward. Use the existing `withdrawBye`, `clearPosition`, `setMatchUpDrawPositions` and result ops. Evaluate the second branch after the first has been folded. Preserve a played downstream result wherever the admitted route only relabels. For deep corrections, visit every changed feeder/side state, including crossings into consolation, playoffs and the decider. Revisiting the same matchUp with a different feeder state is meaningful.
4. **Settling and applying.** Use the §5.1 pass order on the projected graph, including reservations, stale origins, carries past BYEs, missed and unearned links, deciders and scored times. A depth limit on a new traversal cannot replace the writer's observable warning and partial-settlement semantics. Preserve the recorder for exhausted, random, temporal or unsupported paths. Apply the projected operations to the real draw only after admission, landing and settlement all succeed.

## Observable decisions reserved to CA

**VERIFIED contract boundaries** in §§2–5, §5.1 and §7.2 and the exit-propagation rules. Each proposed simplification below would need a ruling. The design preserves the current observable behavior at these boundaries.

| Boundary                       | Observable that a different implementation would change                                                                                                                                                                                           |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Refusal, eligibility and award | Error precedence, code/info/context or state after refusal; returned success, warnings, `connectedStructures`, TEAM result references and nested object identity.                                                                                 |
| Result and provenance          | Stored winner, status, score, retained matchUp format, default process codes, positional vs side reason codes, exact origin/relay fields and missing vs empty fields. A double default over play can keep its score; a double walkover blanks it. |
| Placement and policy           | Actual participant/side and draw position, ordering of assignments, BYE vs vacancy, renumbered sides, group tally, decider and TEAM lineup. Reading the wrong policy or normalizing a converted record changes these.                             |
| Clock and storage              | Creating a missing schedule, keeping/removing scoredTime, entity-specific updatedAt, clock reads and timeItem ordering. A satisfied repeat on an unstamped stored result is the minimal counterexample to treating all repeats as empty.          |
| Notices                        | Topic, order, key/coalescing, payload, originating context, omitted event/tournament fields and subscription-dependent in-context notices. Identical final hashes do not establish notice equivalence.                                            |
| Onward settlement              | Earlier repair, sweeping beyond the current forward bound, losing a warning or consuming a different random choice changes the caller's result or the next call's input.                                                                          |

**BELIEVED first slice.** Prefer a bare, already-stamped lucky double exit asked again over a singleton cell whose only fixture needs a new timestamp. The lucky repeat already has a permanent v1 oracle on five draw sizes. Keep first entry, clear, unstamped repeat, schedule, score, status codes, notes and any outstanding settle work on their existing paths. Qualification requires recorder-off proof, three full suites, step-level harvest and an isolated census delta. Private fixed corpus, production soak and private TEAM fuzz remain owed.
